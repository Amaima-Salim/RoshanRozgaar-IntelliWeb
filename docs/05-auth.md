# 05 — Authentication: Google, Email OTP (Gmail), Demo Phone Login

Read by: Phases 0 (§1–§3), 1 (all), 8 (§6). Sign-in is a team extra (C12); it must never slow down O1.

## 1. Methods (D-12, D-23, D-24, D-25)

| Method | For | Status | Notes |
|--------|-----|--------|-------|
| **Demo phone OTP** | Workers (default), seeded accounts | Mock, disclosed | Fixed `MOCK_OTP_CODE`; the UI says "Demo login — no real SMS is sent"; big numeric keypad, no form |

`AUTH_MODE=mock` (or missing Google/Gmail values) hides Google and email buttons. The demo phone login and demo accounts always work.

## 2. Library and data

- **Better Auth** with its Drizzle adapter and DB-backed sessions in `httpOnly`, `Secure` (prod), `SameSite=Lax` cookies. `SESSION_SECRET` is its secret. Trusted origins are limited to `APP_URL` values.
- Tables are generated by Better Auth's CLI and committed as Drizzle migrations; the user model is mapped to `users` (`docs/02` §3).
- `role` is an additional field with `input: false`, set once via `POST /api/me/role`; afterwards it is immutable.
- The rest of the app uses only `getSession()` and `requireRole()` from `src/lib/auth/guards.ts`; route code never imports the library directly.
- **Check every plugin and option name against the installed version.** Do not copy config from blog posts.

## 3. Demo phone OTP

Rebuild on Better Auth: either its phone-number plugin with a send function that sends nothing plus the fixed code, or a small custom endpoint that creates a Better Auth session after checking `MOCK_OTP_CODE`. Record the choice in `DECISIONS.md`. Rate limit: ≥ 60 s between "sends", ≤ 5 attempts per challenge. Phone-only users get the `<id>@phone.invalid` placeholder email.

## 4. Email OTP over Gmail

- 6 digits, 10-minute expiry, ≤ 5 attempts per code, ≥ 60 s between sends, rate limits per email and per IP.
- Transport (`src/lib/email/transport.ts`): Nodemailer `service: "gmail"`, `GMAIL_USER` + `GMAIL_APP_PASSWORD` (a dedicated project Gmail with 2-Step Verification). Node runtime only (not Edge).
- Template: bilingual plain text + simple HTML; large code; expiry; "We will never ask you for this code."
- **"Code sent" appears only after SMTP accepts the message.** Any failure, including Gmail's daily cap (`550 5.4.5`; a personal account sends about 500 per rolling 24 h), returns `EMAIL_SEND_FAILED` and the UI offers Google or demo login.
- **Never log codes.** Dev only (no Gmail values, `NODE_ENV=development`): print the code to the server console and show "Dev mode — code in server log".

## 5. Google setup (the human supplies; D-28)

- Google Cloud OAuth client (Web). Redirect URIs: `http://localhost:3000/api/auth/callback/google` and `https://<deploy-domain>/api/auth/callback/google` (use Better Auth's actual path if it differs).
- Consent screen: **In production** before the demo (in *Testing*, only listed test users can sign in). Basic scopes need no Google app verification.
- The downloaded `client_secret_*.json` stays **outside the repo**; copy its values into `.env.local` and the host's env settings. Add `client_secret_*.json` to `.gitignore` anyway.

## 6. Linking, roles, sessions

- Google and email OTP with the **same verified email** → one user. Never link on an unverified email; phone-only accounts are never linked.
- First sign-in without a role → role chooser → server sets the role → onboarding.
- Sign-out invalidates the server session and clears client caches (and SW caches in Phase 8).
- Sign-in is **not identity verification**: no "verified" badge or wording anywhere (BR-P12).

## 7. Tests (summary; details in `docs/08`)

Role immutability; OTP happy path, expiry, attempt lockout, reuse, resend throttle; send failure never reports success; same-email linking; unverified email never links; secrets absent from client bundles; E2E demo phone (worker) and stubbed email OTP (customer) on desktop and phone viewports; manual Google test on localhost, the deployed URL and the installed PWA, recorded in the README.
