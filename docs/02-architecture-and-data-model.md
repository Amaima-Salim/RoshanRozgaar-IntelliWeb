# 02 — Architecture and Data Model

Read by: Phases 0, 3, 5 (fully); others as referenced. Pin package versions at build time after checking current stable releases; do not trust version numbers in any doc.

## 1. Principles

1. **The server is the source of truth** for availability, offers, bookings and payments. Clients show server-confirmed state; nothing commits optimistically.
2. **The database enforces the invariants that matter most:** no overlapping confirmed jobs per worker; at most one pending and one successful payment per job.
3. **AI is an adapter, not a dependency.** Every AI call has a timeout, schema validation and a non-AI fallback.
4. **Thin vertical slices.** Domain logic lives in pure, unit-tested functions under `src/lib/domain`.
5. **One responsive codebase.** No separate mobile site. Layout switches by breakpoint (`docs/03` §2).
6. Everything user-visible is i18n-keyed (Urdu/English). No hard-coded UI strings.

## 3. Data model (PostgreSQL; Drizzle schema + hand-written SQL migration)

Conventions: `id uuid pk default gen_random_uuid()`, `created_at timestamptz default now()`, `is_seeded boolean default false` on user-visible data, money = integer PKR.

**Auth tables (Better Auth, generated by its CLI into Drizzle migrations):** `users` (mapped as Better Auth's user model), `sessions`, `accounts` (Google), `verifications` (OTP codes). Better Auth stores codes hashed or as configured; check the installed version. App fields on `users` are Better Auth *additional fields* with `input: false` where clients must not set them.

**Hand-written SQL migration (committed):**
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE jobs ADD CONSTRAINT jobs_no_overlap
  EXCLUDE USING gist (worker_id WITH =, tstzrange(start_at, end_at) WITH &&)
  WHERE (status IN ('confirmed','in_progress'));
CREATE UNIQUE INDEX jobs_one_live_per_request ON jobs(request_id)
  WHERE status IN ('confirmed','in_progress','completed');
ALTER TABLE jobs ADD CONSTRAINT jobs_time_order CHECK (end_at > start_at);
CREATE UNIQUE INDEX payments_one_pending ON payments(job_id) WHERE status = 'pending';
CREATE UNIQUE INDEX payments_one_success ON payments(job_id) WHERE status IN ('succeeded','cash_confirmed');
```

## 4. Consistency design (O4)

`acceptOffer(offerId, actorId, idempotencyKey)` in **one transaction**:
1. Idempotency replay check.
2. `SELECT … FOR UPDATE` the offer (`pending`) and request (`open`); the actor must be the proposer's counterpart in the conversation.
3. Re-check `isWorkerFree`.
4. `INSERT jobs … 'confirmed'`. SQLSTATE `23P01` → `CONFLICT_BOOKED` with next-best alternatives.
5. Offer → `accepted`; sibling offers → `withdrawn`; sibling conversations → `declined`; request → `booked`; `job_events`; store the idempotency response.
6. Commit; return the job with `version`.

Other transitions use optimistic concurrency (`UPDATE … WHERE id=$id AND version=$v AND status=$from`; zero rows → `CONFLICT_STATE` with the current row). Use a pooled driver with real transactions (`postgres`/`pg` over Neon's pooled URL), never an HTTP-only driver, on booking and payment paths.

## 5. Availability

`isWorkerFree(worker, start, end, now)`: toggle ON (enforced only when `start` is within 15 min of `now`); `[start,end]` inside a schedule window for the Asia/Karachi weekday; no `confirmed|in_progress` job overlapping. Pure function + one overlap query; candidates and booking both call it; the DB constraint is the final arbiter.

## 6. Ranking (design choice, versioned)

1. **Filter:** trade, ≤ radius, `isWorkerFree`, onboarding complete, not the requester.
2. **Score:** `0.40·proximity + 0.30·rating + 0.15·experience + 0.15·priceFit`. `proximity = 1 − min(d/R,1)`; `rating = (bayes−1)/4`, `bayes = (C·m + Σstars)/(C+n)`, `C=3`; `experience = min(years,15)/15`; `priceFit` = 1 if rate ≤ budget else `max(0, 1 − (rate−budget)/budget)`, 0.5 without a budget.
3. Tie-break: distance, then id. Return `reasons[]` per worker ("2.1 km away", "free at 3:00 pm", "4.6★ from 18 customers"). Weights live in `ranking-config.ts` with `RANKING_VERSION`.
4. `no_match` with suggestions (widen radius / change time). Never fabricate.
5. Public worker coordinates are rounded (~500 m).

## 7. API surface (route handlers; JSON; authz on every route)

| Route | Method | Who | Purpose |
|-------|--------|-----|---------|
| `/api/auth/*` | * | public | Better Auth handler: Google OAuth callback, email OTP send/verify, demo phone OTP, sign-out |
| `/api/me` | GET/PATCH | any | Profile basics, language; `POST /api/me/role` sets role once |
| `/api/ai/transcribe` | POST multipart | auth | STT with fallback chain |
| `/api/ai/extract-worker-profile` | POST | worker | Transcript/answers → validated profile draft |
| `/api/ai/draft-request` | POST | customer | Text/transcript/photo → request draft |
| `/api/ai/translate` | POST | auth | Voice-note/text translation |
| `/api/ai/draft-offer` | POST | participants | Voice note → draft offer terms (human sends) |
| `/api/ai/summarize-review` | POST | customer | Comment → tags + bilingual summary |
| `/api/worker/profile` | GET/PUT | worker | Confirmed profile + schedule + toggle |
| `/api/worker/inbox` | GET | worker | Requests/conversations with match reasons |
| `/api/requests` | POST/GET | customer | Create / list own |
| `/api/requests/[id]/candidates` | GET | owner | Ranked workers or `no_match` |
| `/api/workers/[id]` | GET | auth | Public card + reputation + recent reviews |
| `/api/conversations` | POST | customer | Start conversation |
| `/api/conversations/[id]/messages` | GET `?after=seq` / POST | participants | Poll / send (`client_msg_id`) |
| `/api/conversations/[id]/offers` | POST | participants | Create/counter |
| `/api/offers/[id]/{accept,decline,withdraw}` | POST | counterpart/proposer | `accept` = atomic booking; `Idempotency-Key` |
| `/api/jobs/[id]` | GET | participants | Job + version + events + payment status |
| `/api/jobs/[id]/transition` | POST | role-specific | start / request-complete / confirm-complete / cancel |
| `/api/jobs/[id]/review` | POST | customer | Review (completed only) |
| `/api/jobs/[id]/cash` | POST | participants | Cash tap (worker "received" / customer "paid") |
| `/api/payments` | POST | job's customer | Start payment `{jobId, provider}` + `Idempotency-Key`; amount from server |
| `/api/payments/[id]` | GET | participants | Payment status (polled) |
| `/api/payments/jazzcash/return` | POST | gateway | Verify hash → inquiry → update; no session |
| `/api/payments/easypaisa/callback` | POST | gateway | Same pattern (sandbox mode only) |
| `/api/payments/mock/return` | POST | auth (mock mode) | Mock provider through the same verify/update path |
| `/api/media/[id]` | GET | owner or participant | Stream audio/image |
| `/api/health` | GET | public | DB + config check, no secrets |

**Error contract:** `{ ok:false, error:{ code, messageKey, details?, current? } }`, with codes `UNAUTHENTICATED, FORBIDDEN, VALIDATION, NOT_FOUND, CONFLICT_BOOKED, CONFLICT_STATE, RATE_LIMITED, AI_UNAVAILABLE, PAYLOAD_TOO_LARGE, EMAIL_SEND_FAILED, PAYMENT_UNAVAILABLE, PAYMENT_VERIFICATION_FAILED`. Success: `{ ok:true, data }`. Clients map `messageKey` to Urdu/English.

**Polling:** React Query/SWR `refreshInterval` 4 s while visible and online; chat uses `?after=seq`; jobs and payments use `version`; pause when hidden or offline.

## 9. Observability
Structured server logs with `requestId`. Never log audio, transcripts, phone numbers, emails, OTPs, tokens, keys, hashes or salts. Friendly keyed errors; no stack traces to clients. Log AI/email/payment provider failures by class (timeout / 429 / invalid output / verification failed).
